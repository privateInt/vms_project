# 단위 07-B — 장치 수정 저장소·스키마 4

작성일: 2026-09-30 · 코드·로컬 검증 및 PostgreSQL 17.11 서버 격리 검사 완료

## 선행 결과와 범위

07-A 계약 패치 5개의 서버 적용을 확인했다. 사용자 로그의 백업은 `var/patch-backups/step07a-62qr5anw`, 서비스 재시작 및 운영 활성화 필요 여부는 모두 false다. 현재 운영 camera는 단위 06의 `0.3.1-source-list`, DB는 스키마 3이다.

작업 원칙에 따라 이번에는 장치 수정 저장소·추가 SQL·최소 권한·필수 격리 검사만 구현한다. HTTP PATCH 연결·운영 마이그레이션·이미지 전환·소스 수정/삭제·장비 연결은 후속 단위다.

## 구현

- DeviceUpdate 저장소 입력과 유효성 검사: schema_version, expected_version, display_name. 유효한 ID·키·주체와 요청인지 DB 접근 전에 확인한다. HTTP 원문 디코더와 라우트는 추가하지 않았다.
- `UpdateDevice`: 주체·PATCH·정규 장치 경로·키로 멱등 범위를 분리한다. 같은 범위의 성공 기록을 먼저 확인하고 최초 성공 스냅샷을 재생한다. 새 요청은 장치 행을 잠근 뒤 version을 비교하고 이름과 version/updated_at만 갱신한다.
- 이름 변경과 성공 스냅샷을 같은 트랜잭션으로 확정한다. 응답 기록 저장 실패 시 장치 변경도 롤백한다. 같은 이름의 새 명령도 version+1, 같은 성공 요청의 재생은 추가 변경 없음이라는 07-A 계약을 유지한다.
- 없는/삭제된 장치, 버전 충돌, 멱등 충돌, bigint 버전 소진을 구분한다. updated_at은 서버 UTC를 사용하되 이전 시각보다 감소하지 않는다.
- `0004_device_update.sql`: PATCH 성공 기록 테이블 추가. 과거 마이그레이션은 수정하지 않는다. 빈 DB 4/4, 스키마 3→4에서 1/4, 재적용 0/4다.
- runtime 권한은 새 요청 테이블 SELECT/INSERT 및 devices의 display_name·version·updated_at 열 UPDATE만 추가한다. readiness도 스키마 4와 필요한 권한을 검사한다.

기존 장치 생성·조회와 소스 등록·조회 코드는 유지한다. 새 공통 저장소의 readiness를 사용하는 기존 API 통합 시험 계정과 마이그레이션 기대값만 스키마 4에 맞췄다. 실행 OpenAPI와 API 버전·라우팅에는 변경이 없고 PATCH는 여전히 미구현이다.

## 검증

- Go 1.27.1의 전체 `go test -p 1 -race ./...`와 `go vet ./...` 통과. DB 미설정 실행의 통합 검사는 skip되므로 다음 별도 결과와 구분한다.
- PGlite / PostgreSQL WASM 브리지에서 app·storage 패키지를 각각 새 DB로 검사했다. 최초 실행은 새 장치 수정 검사들을 통과한 뒤 기존 소스 검사에서 연결 재설정 오류로 끝났다. 코드 변경 없이 새 시험 DB로 한 번 재실행해 두 패키지 전체가 통과했다. 이를 실제 PostgreSQL 서버의 장애나 운영 장애로 판단하지 않는다.
- 새 저장소 검사에서 스키마 3→4 기존 데이터 보존, GET/목록과 수정 결과 일치, 자식 소스·프로필 보존, 기존 POST 멱등 응답 보존, 이후 수정·풀 재접속 후 과거 PATCH 응답 재생, 키·경로·주체 분리, 응답 저장 실패의 전체 롤백과 재시도, 같은 이름 수정, tombstone·버전 최댓값·시각 감소 방지를 확인했다.
- 실제 권한·동시 세션 검사는 WASM에서 skip한다. 서버 검사에 동일 키 8개 요청의 단일 수정과 재생, 서로 다른 키의 버전 경쟁, 같은 키의 다른 본문 경쟁, 실제 runtime 로그인·열별 UPDATE·금지된 수정/삭제/DDL 차단, 권한 회수 시 readiness 실패와 롤백·동일 키 재시도를 포함했다. 아직 해당 서버 결과를 받지 않았다.
- 파일 패치 적용·재적용, 기존 환경·운영 활성화 기록 보존, 마이그레이션 0001~0003 불변과 코드 명세 해시를 확인했다.

Go 서비스의 HTTP 프로세스·라우팅 구현은 바꾸지 않았다. 기존 실제 API 프로세스 재시작·목록·등록 회귀 검사는 위 app 통합 검사에 포함됐다. 이번에 운영 이미지 빌드나 서비스 전환을 실행하지 않았다.

## 전달과 다음 기준

README·문서 목록·저장소 안내·프로젝트 명세를 현재 단계에 맞췄다. 코드의 목표 스키마는 4, 인수된 운영 스키마는 3으로 구분한다. 과거 04·05·06 전환 도구는 해당 리비전 전용이며 새 명세에서 재사용하지 않는다. 과거 보고서와 백업은 보존한다.

파일 적용만으로 운영 DB나 실행 이미지가 바뀌지 않는다. 서버에서는 기존 격리 실행 도구로 이번 코드를 별도 `vms-storage-test-*` 프로젝트에서 검사한다. 마지막 `status=passed`, `scope=camera_device_update_storage_native_postgresql`, `production_services_modified=false`를 받으면 **07-C 장치 수정 HTTP API 연결**로 진행한다. 서버 격리 검사가 실패하면 이번 저장소 범위에서 먼저 수정한다.

스키마 4의 실제 운영 반영은 07-C와 별도 전환 검증 이후다. 스키마 4를 적용한 DB에 기존 스키마 3 이미지만 복귀하는 방식은 사용할 수 없다. 자동 운영 DB 복원은 수행하지 않는다. 패치 적용 명령은 채팅에서만 제공한다.
