## 이번 범위와 변경

작업 원칙에 따라 이번 단위는 검증된 이미지로 운영 camera API만 전환하는 도구·필수 테스트·문서·패키지에 한정한다. 기존 기능 코드와 스키마, Compose 및 프로젝트 명세는 유지한다. 수정·삭제·장치 연결·영상 입력·UI 등 다음 기능은 시작하지 않는다.

- `activate_camera_source_list.py`: 06-B1 보고서·이미지·코드 일치 확인, 환경 이미지 ID만 교체, camera API만 전환, readiness·버전·목록 GET 검증, 완료 기록. 실패 시 조건이 유지되면 이전 이미지로만 복귀한다.
- `test_source_list_activation_unit.py`: 전환·재실행·실패·동시 변경의 경계를 검증한다.
- [운영 전환 안내](../operations/camera-source-list-activation.md)와 이 진행 기록을 추가한다.

도구가 호출할 수 있는 Docker 변경 명령은 이미지 ID를 지정한 camera API 단독 전환으로 제한한다. 의존 서비스 기동·빌드·이미지 다운로드는 차단한다. DB 접근은 읽기 전용 SQL이며 마이그레이션·권한 부여·DB 복원은 수행하지 않는다. 기존 05 활성화 기록 및 DB 백업은 덮어쓰지 않는다.

설정 전환 기록에는 원래 환경 파일과 컨테이너 상태를 보관한다. 실제 적용 중 잠시 camera API 요청이 중단될 수 있다. 이미지 교체 전후의 등록 데이터를 없애는 DB 복구는 자동 실패 처리에도 포함하지 않는다. 동시 수정이나 예상 밖 상태는 보존하고 확인이 필요한 결과로 기록한다.

## 검증

- Python 실패 경계 테스트 13개 통과: 성공 후 재실행 무재시작, 오래된/다른 검사 결과 거부, 이전 이미지 누락 시 차단, 새 이미지 확인 실패 시 복귀, Compose 중간 실패 시 복귀, 환경 동시 수정 보존, DB 컨테이너·스키마 변경 시 중단, 이전 이미지 복귀 자체의 실패 기록, 실패/중단 이력 재실행 차단, 이미지 설정 후 실행 전 오류 복구, 환경 바이트 보존, Docker 변경 명령 제한.
- Compose 5.5.1로 환경 변경 전후를 오프라인 해석해 camera 관련 이미지 참조만 달라지고 주소·DB·다른 서비스 설정은 같은 것을 확인했다. 사용한 기동 옵션도 설치된 Compose 도움말로 확인했다. 활성화 도구에 적용 옵션이 없으면 전환하지 않고 종료하는 것을 확인했다.
- 파일 4개 패치의 적용·재적용, 기존 코드 명세·환경 파일·05 활성화 기록·06-B1 통과 보고서 보존을 확인했다.
- Go 코드와 기존 API 프로세스·라우팅 구현은 바꾸지 않았다. 이미 서버에서 통과한 06-A 기능 검사 및 06-B1 실제 이미지 검사를 반복 실행하지 않는다.

현재 로컬 환경에는 Docker 엔진이 없어 새 전환 도구의 실제 운영 실행은 검증하지 못했다. 실패 경계 테스트는 제어된 Docker·HTTP 대체 객체를 사용한다. 06-B1의 실제 이미지 호환성 증거와 이번 도구의 로컬 검증을 구분하며, 실제 활성화 완료는 사용자 서버 실행 결과를 받은 뒤 기록한다.

## 다음 완료 기준

서버에서 `status=activated`, `scope=camera_source_list`, `source_list_activated=true`, `schema_version=3`, `migration_applied=0` 및 DB·다른 서비스 유지 결과를 확인한다. 이미 완료한 뒤 재실행한 경우 `already_activated`와 재시작 없음도 유효한 확인 결과다. 그 결과를 받으면 단위 06 운영 인수 기록을 마무리한다. 실패하면 전환 기록에 근거해 이번 범위의 원인만 해결한다.

패치 적용 명령은 작업 원칙에 따라 문서에 넣지 않고 채팅으로 전달한다.
