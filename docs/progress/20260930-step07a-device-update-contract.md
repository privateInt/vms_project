# 단위 07-A — 장치 표시 이름 수정 계약

작성일: 2026-09-30 · 계약·예제·계약 검사 완료 · API/저장소 구현 및 운영 활성화 전

## 선행 단계 인수

단위 06 소스 목록 API의 운영 전환에 이어 완료 기록 문서 1개의 서버 적용을 확인했다. 사용자 로그는 `status=applied`, `written=1`, `service_restart_performed=false`, `runtime_activation_required=false`다. 백업은 `var/patch-backups/step06-notes-acaexwut`다. 단위 06의 기능·운영 전환·완료 기록 반영까지 인수를 마쳤다.

현재 운영 camera는 `0.3.1-source-list`, DB는 스키마 3이다. 이번 단위는 작업 원칙에 따라 장치 수정 계약 하나에 한정한다.

## 확정한 내용

- `PATCH /api/v1/devices/{device_id}`에서 display_name만 수정한다. device_id·device_kind는 불변이며 자식 소스가 있어도 이름 수정은 가능하다.
- 본문은 schema_version, expected_version, display_name이다. 조회한 version과 일치하는 새 요청만 성공하고 version은 1 증가한다. 같은 이름의 새 명령도 이 규칙을 따르며 동일 멱등 요청의 재생은 증가시키지 않는다.
- Idempotency-Key를 요구한다. 장치 변경과 최초 성공 스냅샷을 원자적으로 저장하고, 응답 유실 후 같은 키·본문의 재시도는 최초 성공을 재생한다. 서로 다른 키가 같은 version을 수정하면 하나만 성공한다.
- 버전 불일치와 멱등 키 충돌을 별도 409 코드로 구분한다. 현재 상태는 GET으로 확인하며 재생된 과거 응답이 장치를 되돌리지 않는다.
- 기존 06의 실행 OpenAPI·Go·Compose·마이그레이션·프로젝트 명세를 바꾸지 않는다. 따라서 현재 실행 API에는 PATCH가 없으며 계약 패치만으로 사용할 수 없다.

계약 원본은 camera 소유의 `src/platform/camera/api/planned` 아래 스키마와 예제에 두고, 설명과 상태 규칙은 [장치 수정 계약](../contracts/camera-device-update.md)에 기록했다. 검사 코드도 같은 소유 플랫폼의 계약 옆에 둔다. 소스 수정·삭제·장비 연결·UI는 이번 범위에 포함하지 않는다.

## 확인한 구현 영향

현재 runtime 역할에는 UPDATE 권한이 없고, 기존 장치 생성 요청 테이블은 POST 전용이다. 다음 저장소 단위는 새 수정 요청 기록 테이블과 최소 갱신 권한, 추가 마이그레이션을 준비해야 한다. 목표는 스키마 4이며 이번 단계에서 적용하지 않는다.

기존 06 API가 정확한 스키마 3 이력을 확인하므로 향후 스키마 4 전환에 기존 06의 이미지 복귀 절차를 재사용할 수 없다는 점을 계약에 기록했다. 후속 배포는 별도 호환성·복구 검증을 거쳐야 하며 자동 운영 DB 복원은 허용하지 않는다.

## 이번 검증과 한계

예정 요청 JSON Schema와 예제, 필수/nullable 여부, 불변·비밀 필드 차단, version 경계·타입, Unicode 이름 제한, 기존 생성 입력의 이름 규칙 일치, 현재 OpenAPI에 PATCH를 잘못 표시하지 않았는지를 검사했다. 계약 검사 8개가 통과했다.

스키마 검사는 파싱된 값의 정적 검증이다. 원문 JSON 중복 키·정수 표기, 실제 HTTP 상태 코드·인증·재시도·동시성·DB 권한·원자성은 아직 구현하거나 실행 검사한 것이 아니다. 해당 사항은 후속 단위의 완료 기준으로 남겼다. Go 변경이 없어 Go/DB 통합 검사나 이미지 빌드를 반복하지 않는다.

패치는 새 파일 5개만 추가한다. 파일 적용·재적용과 기존 코드 명세·운영 환경·활성화 기록 보존을 확인했다. 사용자 서버에 이번 패치가 적용됐다는 확인은 아직 받기 전이다. 패치 적용 명령은 채팅으로만 전달한다.
