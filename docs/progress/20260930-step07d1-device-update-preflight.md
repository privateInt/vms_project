# 단위 07-D1 — 장치 수정 운영 전환 사전점검

작성일: 2026-09-30 · 사전점검 도구·로컬 검증 완료 · 실제 서버 점검 결과 대기

## 07-C 서버 격리 검사 인수

사용자 로그에서 07-C 패치 21개 적용을 확인했다. 백업은 `var/patch-backups/step07c-2g7ejqa3`이며 파일 적용 중 서비스 재시작이나 운영 활성화는 수행하지 않았다.

`vms-storage-test-07ad42467fb1`의 PostgreSQL 17.11에서 전체 Go race 검사와 vet가 통과했다. 다음 항목이 실제 서버에서 확인됐다.

- PATCH 입력·정수 토큰·헤더·오류 순서·본문 제한.
- 장치명 수정, 정규 JSON/경로의 멱등 재생, 버전·키 충돌과 버전 소진.
- GET/목록 반영, 자식 소스·프로필과 POST 응답 보존, 같은 이름 수정의 버전 증가.
- API 프로세스 재시작·토큰 교체 후 과거 PATCH 응답 재생과 현재 상태 보존.
- runtime 권한 회수 시 PATCH/readiness 503, 전체 롤백, 권한 복구 후 같은 키 재시도.
- 기존 저장소의 스키마 3→4·최소 권한·동시 요청 검사와 장치/소스 API 회귀.

최종 결과는 `status=passed`, `scope=camera_device_update_http_native_postgresql`, `production_services_modified=false`다. 전용 DB 컨테이너와 네트워크가 제거됐다. 이전 07-C 문서의 서버 검사 대기는 작성 당시 상태이며 이 결과로 해소됐다. 실제 운영 camera는 여전히 단위 06의 `0.3.1-source-list`와 스키마 3이다.

## 이번 단위의 범위

`src/infra/tools/inspect_camera_device_update.py`는 운영 전환을 준비하기 위한 읽기 전용 점검이다. 이번 패치는 점검 도구·해당 테스트·이 기록의 3개 파일만 추가한다. 검증한 07-C 프로젝트 명세와 기존 파일의 해시를 그대로 유지하며 새 파일은 패치 명세로 검증한다. 검사 보고서에는 점검 도구 자신의 해시도 기록한다.

Docker 명령은 프로젝트/컨테이너/볼륨 조회, 현재 Compose 구성 조회와 고정 읽기 전용 SQL만 허용한다. HTTP는 readiness·platform·소스 목록 GET만 요청한다. 이미지 빌드, 컨테이너 생성·정지·재시작, 마이그레이션·권한 부여, DB 백업/복원, POST/PATCH 요청은 수행하지 않는다.

로컬 쓰기는 기존 activation 잠금과 `var/camera/device-update-preflight.json` 보고서뿐이다. 잠금은 앞선 전환 도구와 공유한다. 비밀·환경 파일을 생성하거나 수정하지 않는다.

## 확인 항목과 중단 조건

- 07-C 코드 버전 `0.4.0-device-update`·저장소 리비전·명세에 기록된 모든 파일의 SHA-256.
- 로컬 Unix Docker, `vms-project`의 실행 중인 camera API/DB, 기존 영속 볼륨 소유권과 실제 DB 마운트·health.
- 06 완료 기록 `source-list-activation.json`의 completed/activated 상태 및 현재 API/DB 이미지 일치. 현재 Compose도 실행 중인 camera 이미지 ID로 고정돼 있어야 한다.
- 기존 비밀 디렉터리/파일 소유권·권한·DSN 형식과 실제 camera의 읽기 전용 runtime DSN 마운트.
- 운영 API `0.3.1-source-list`, source_list 단계·capability, readiness와 목록 GET 성공.
- PostgreSQL 17, 기존 마이그레이션 0001~0003의 이력·이름·체크섬 일치, device_update_requests 테이블 부재. 이미 스키마 4이거나 중간 상태이면 중단한다.
- 운영 역할의 관리자 권한 여부, runtime 외의 동시 DB 클라이언트, 장치·생성 응답 기록·소스·프로필·소스 생성 응답 기록 건수.
- DB 크기와 호스트 백업 경로의 가용 공간. 준비 단계의 최소 공간 기준은 DB 크기의 2배와 64 MiB 중 큰 값이다. 이는 여유 공간 점검 기준이며 실제 덤프 크기나 복원 성공의 증거는 아니다.
- 점검 전후 컨테이너 ID/이미지/시작 시각/재시작 횟수, 환경·비밀·06 완료 기록·07-C 명세·점검 도구 해시 유지.

건수는 정상 업무 요청이 계속 가능한 상태에서 읽는 시점 값이다. 운영 쓰기를 차단하거나 데이터 백업을 생성하지 않는다. 원문 이름·프로필·토큰·DSN·비밀번호는 보고서와 표준 출력에 포함하지 않는다. 환경/비밀 해시·컨테이너/데몬 식별자는 0600 개인 보고서에만 둔다. 표준 출력은 상태·버전·건수·공간·이미지 등의 요약이다.

잠금 획득 후에는 이전 보고서를 running으로 바꾸고 실패/중단 시 failed로 덮어쓴다. 다른 작업이 잠금을 잡고 있으면 보고서를 덮어쓰지 않고 중단한다. 상세 Docker 오류 대신 고정 오류 코드만 출력한다. 성공 보고서만으로 후속 운영 전환을 허가하지 않으며 전환 검증 단계에서 당시 코드·상태를 다시 확인한다.

## 로컬 검증

- 새 도구의 Python 테스트 23개 통과. 읽기 전용 허용 명령, 빌드/재시작/삭제/임의 SQL 차단, 정상 결과와 원본 보존, 스키마·체크섬·API·완료 기록·이미지·마운트·권한·클라이언트·건수·공간 오류를 확인했다.
- 점검 중 환경·비밀·컨테이너 변경, 코드 변경, 심볼릭 링크, 기존 성공 보고서의 실패/중단 무효화, 공유 잠금 충돌, 보고서 0600과 오류 비밀 비노출을 확인했다.
- PGlite의 임시 스키마 3에서 고정 읽기 전용 SQL을 실행해 마이그레이션 3개·건수 필드 5개·수정 테이블 부재의 결과 구조를 확인했다. 실제 PostgreSQL 17/Docker의 운영 사전점검은 사용자 서버에서 수행할 단계다.
- 패치 적용·재적용, 기존 모든 코드·명세·환경·운영 기록 보존, 새 파일 해시를 확인했다. Go·라우팅·SQL 마이그레이션 변경이 없어 앞선 Go/DB 전체 검사와 smoke는 다시 실행하지 않았다.

## 서버 실행 결과와 다음 단위

성공 scope는 `camera_device_update_preflight`, 현재 schema_version=3, target_schema_version=4다. production_services_modified=false, device_update_activated=false를 유지한다. 구체적인 현재 건수·공간·이미지는 사용자가 실행한 결과로 확정한다. 아직 서버에서 사전점검이 통과했다고 기록하지 않는다.

성공 로그를 받으면 다음 작은 단위는 **07-D2: 스키마 4 전환과 복구의 격리 리허설**이다. 실제 운영 마이그레이션·이미지 전환은 그 이후 별도 단계다. 스키마 4에 기존 스키마 3 이미지만 복귀시키는 절차나 자동 운영 DB 복원은 사용하지 않는다. 적용·실행 명령은 채팅에서만 제공한다.
