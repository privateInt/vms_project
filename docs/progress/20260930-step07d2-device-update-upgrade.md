# 07-D2 — 장치 수정 스키마 전환·복구 격리 리허설

## 이번 단위

07-D1 서버 사전점검 통과를 인수하고, 별도 Docker 프로젝트에서 스키마 3→4 전환과 별도 DB 복원을 검증하는 도구를 추가했다. 이번 패치는 도구·테스트·진행 기록 3개 파일만 추가한다. 07-C의 제품 코드·마이그레이션·프로젝트 명세와 07-D1 파일은 변경하지 않는다.

작업 시작 시 AGENTS.md, 작업 원칙 문서와 최신 진행 기록을 확인했다. 한 번에 독립적인 단위 하나를 완결하는 원칙에 따라 운영 전환 도구 구현은 다음 단위로 남긴다.

## 리허설 범위

`src/infra/tools/test_camera_device_update_upgrade.py`는 다음을 수행한다.

1. 07-D1 읽기 전용 검사로 현재 운영 상태·명세·이미지·비밀 파일·컨테이너를 확인한다.
2. `vms-device-update-test-` 접두사와 무작위 식별자를 가진 프로젝트를 별도 임시 경로에 만든다. 명세에 기록된 코드만 복사하고 임시 비밀과 loopback 포트를 새로 만든다. 운영 DB와 같은 이미지 ID를 사용하되 볼륨은 별개다. 같은 프로젝트의 기존 컨테이너·볼륨·네트워크 또는 후보 이미지 태그가 있으면 중단한다.
3. 후보 camera 이미지를 빌드한다. 이전 camera 이미지로 빈 시험 DB를 스키마 3까지 구성하고 장치, 소스 2개와 프로필을 등록한다. 운영 데이터는 복사하지 않는다.
4. 시험 API를 정지하고 DB 클라이언트가 없는지 확인한다. 시험 DB의 스키마 3 덤프를 만든 뒤 후보 이미지로 스키마 4 마이그레이션과 runtime 권한을 적용한다. 재적용 0건, 이력 체크섬과 테이블·열 권한을 확인한다.
5. 기존 장치·소스 생성 응답 재생, 프로필과 소스 목록·기존 커서를 확인한다. 장치 이름을 두 번 수정하여 버전 2·3을 만들고, 동일 키 재생과 키 충돌·버전 충돌을 확인한다. POST와 PATCH에서 같은 키를 사용해 메서드별 범위도 확인한다.
6. 전환 후 새 소스를 등록하고 후보 API를 재생성한다. 첫 PATCH는 과거 버전 2를 재생하고 GET/목록은 최신 버전 3을 반환하는지, POST는 최초 생성 응답을 유지하는지 확인한다.
7. 스키마 3 덤프를 시험 DB 컨테이너의 별도 `vms_camera_restore` 데이터베이스에 복원한다. 별도 DSN과 포트의 이전 API로 기존 장치·소스·응답 재생·목록을 확인한다. 스키마 4 DB의 수정 이력과 전환 후 새 소스가 보존되는지 다시 확인한다.
8. 시험 DB 컨테이너와 model/analysis/operation 시험 컨테이너가 유지됐는지 확인하고, 해당 시험 프로젝트의 컨테이너·볼륨·네트워크를 정리한다. 이후 운영 상태를 다시 읽어 비교한다.

후보 이미지는 후속 전환에서 검증한 이미지 ID를 사용할 수 있도록 남긴다. 시험 덤프·DB·비밀은 성공 시 임시 경로와 함께 정리된다. 이 덤프는 운영 백업이 아니다.

운영에는 조회와 공유 activation 잠금·결과 보고서 기록만 수행한다. 운영 API 정지·재시작, POST/PATCH, 마이그레이션·권한 변경, DB 백업·복원을 수행하지 않는다. 운영 건수는 정상 요청으로 변할 수 있어 전후 동일성을 강제하지 않는다. 운영 컨테이너·이미지·환경·비밀·06 완료 기록·코드와 리허설 도구의 해시는 유지돼야 한다.

실패와 키보드 중단도 시험 자원 정리를 시도한다. 정리가 실패하거나 자원이 남아 있으면 성공으로 기록하지 않고, 연결된 비밀 파일이 사라지지 않도록 임시 경로를 보존하여 출력한다. 생성 전 충돌로 중단한 프로젝트에는 정리 명령을 실행하지 않는다. 실패/중단 시 이전 성공 보고서를 failed로 무효화한다.

## 로컬 검증

- Python 테스트 21개 통과: 격리 프로젝트·경로 제한, 운영 변경 명령 차단, 복원 DSN 분리, 명세 변경과 자원 충돌 중단, 실패·중단 정리와 정리 실패 시 파일 보존, 스키마·권한·응답 검증, 운영 상태 변경 감지, 보고서 무효화·0600·오류 비밀 비노출.
- Docker Compose 오프라인 구성 해석 통과: 7개 서비스, 새/이전 camera 이미지 분리, DB 이미지 고정, 전용 볼륨, 내부 DB 네트워크, loopback 포트와 임시 비밀 경로 확인. Docker 엔진은 실행하지 않았다.
- PGlite 임시 스키마 4에 실제 마이그레이션과 코드의 runtime GRANT SQL을 적용하고, 새 도구의 스키마 이력·권한·역할 조회 SQL을 실행했다. 마이그레이션 4개와 제한된 UPDATE 권한 확인. 이는 native PostgreSQL 복원·Docker 실행 검증을 대신하지 않는다.
- 패치 적용·재적용과 새 파일 해시, 기존 코드·명세·환경·운영 기록 보존을 확인했다.
- 제품 Go 코드·라우팅·마이그레이션 변경이 없어 이미 서버에서 통과한 07-B/07-C의 Go·DB 전체 검사를 반복하지 않았다.

## 서버 검증과 다음 단위

사용자 서버에서 native Docker 리허설 실행이 남아 있다. 아직 후보 이미지 빌드·스키마 전환·덤프 복원에 성공했다고 기록하지 않는다.

성공 결과는 scope=`camera_device_update_upgrade_native_docker`, status=passed다. 결과에 후보/이전/DB 이미지 ID, 스키마 4 검증과 응답 재생·복원·데이터 보존 결과를 담는다. production_services_modified=false, device_update_activated=false, isolated_resources_removed=true, automatic_production_database_restore=false여야 한다. 개인 보고서는 `var/camera/device-update-upgrade-check.json`이다. 적용·실행 명령은 채팅에서만 제공한다.

이 결과를 인수한 뒤 다음 단위는 **07-D3: 검증한 후보 이미지와 스키마 4의 운영 전환 준비**다. 실제 전환 전에 코드·이미지·운영 상태를 다시 확인해야 한다. 스키마 4에서 스키마 3 이미지만 복귀시키거나 운영 DB를 자동 복원하는 절차는 사용하지 않는다. 업무 런타임 전체가 준비됐다는 의미도 아니다.
