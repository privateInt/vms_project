현재 운영 API는 `0.4.0-device-update`, 스키마는 4다. 목표는 `0.5.0-source-update`, 스키마 5다. 장치·장치 생성 이력·소스·프로필·소스 생성 이력·장치 수정 이력의 6개 건수는 모두 0이었다. DB 크기는 7,968,435바이트, 호스트 백업 여유 공간은 222,067,027,968바이트로 최소 67,108,864바이트 기준을 충족했다.

- 현재 DB 이미지: `sha256:248efd5e58cd743f2a0e0daec8ea4649e5580145ec2a12e2345bc710d4a77201`

[08-D1 기록](20261001-step08d1-source-update-preflight.md)의 서버 결과 대기는 이 로그로 해소됐다. 이번 리허설은 실행 직전에 운영 상태를 다시 읽어 현재 기준을 확정한다.

## 이번 변경

`src/infra/tools/test_camera_source_update_upgrade.py`, 해당 Python 단위 테스트, 이 진행 기록의 3개 파일을 추가한다. 08-C 프로젝트 명세와 기존 파일의 해시는 유지하고 새 파일은 패치 명세로 검증한다. 제품 Go 코드·API·마이그레이션·운영 Compose 변경은 없다.

작업 기준의 한 번에 한 단위 원칙에 따라 이번 완료 범위는 **격리 리허설 도구와 전달 패키지**다. 운영 전환 도구는 다음 단위로 둔다. 적용·실행 명령은 채팅에서만 제공한다.

## 서버에서 수행할 리허설

1. 운영 API·DB 이미지 ID와 08-C 코드 명세를 확인한다. 별도 임시 작업 공간과 무작위 `vms-source-update-test-` 프로젝트, 새 비밀값·볼륨·네트워크·loopback 포트를 사용한다. 후보 camera 이미지를 이 공간에서 빌드한다. DB 이미지는 현재 운영 이미지 ID로 고정한다.
2. 이전 camera 이미지로 빈 시험 DB를 스키마 4까지 구성한다. 장치 등록과 장치 이름 수정, 프로필이 있는 소스 2개 등록, device_id 필터가 포함된 목록 cursor를 준비한다. 운영 데이터 건수가 0이어도 시험 데이터·수정 이력을 만들어 검증한다.
3. 시험 API를 정지하고 다른 DB 클라이언트가 없음을 확인한 뒤 시험 DB를 덤프한다. 새 이미지로 스키마 5와 runtime 권한을 적용하고 재실행 시 추가 마이그레이션 0건인지 검사한다. 0001~0005의 이름·순서·체크섬과 수정 이력 테이블을 검증한다.
4. 새 API에서 기존 장치·소스 등록 응답과 장치 수정 이력, cursor를 확인한다. 소스 이름을 두 번 수정하고 각 버전·시각·불변 필드·프로필 순서를 검사한다. 과거 PATCH 성공 응답 재생, 키 충돌·버전 충돌을 확인한다. 장치 PATCH도 독립적으로 계속 동작하는지 확인한다.
5. 전환 후 소스를 추가하고 API 컨테이너를 재생성한다. 장치·소스의 과거 PATCH 응답과 최초 POST 응답은 각각 보존되며 최신 GET·목록은 최신 상태인지 검사한다. 부모 장치·형제 소스·프로필, 목록·필터·기존 cursor도 확인한다.
6. 덤프를 같은 시험 DB 컨테이너의 **별도 `vms_camera_restore` 데이터베이스**에 복원한다. 별도 DSN과 포트의 이전 API로 스키마 4, 전환 전 장치 수정 이력·소스·프로필·cursor를 검사한다. 전환 후 소스는 이 복원 DB에 없어야 한다.
7. 스키마 5 DB의 최신 장치·소스와 과거 응답·전환 후 추가 데이터가 그대로인지 재확인한다. 시험 DB 컨테이너와 model/analysis/operation 대신 띄운 시험용 컨테이너 3개의 상태가 유지되는지 확인한다. 시험 컨테이너·볼륨·네트워크를 정리하고 후보 이미지를 후속 전환 검증용으로 남긴다.

runtime은 장치·소스의 display_name/version/updated_at 열에만 UPDATE할 수 있어야 한다. 등록·수정 이력과 프로필에 SELECT/INSERT 외 변경 권한이 없어야 하고, 소스 식별자·부모·채널·전송 방식·primary profile 등 불변 열의 UPDATE가 금지돼야 한다. migrator/runtime의 관리자 권한도 검사한다.

## 운영 경계와 실패 처리

운영 핸들은 08-D1의 읽기 전용 Docker 래퍼를 사용한다. 운영 API GET·구성 조회·고정 READ ONLY SQL만 수행하며 운영 DB 백업·복원·마이그레이션·권한 부여·POST/PATCH·서비스 재시작을 실행하지 않는다. 운영 로컬 쓰기는 공유 activation 잠금과 0600 검사 보고서다.

운영 데이터 건수는 정상 요청으로 변할 수 있어 전후 동일성을 강제하지 않는다. 운영 컨테이너·이미지·환경·비밀·07 완료 기록·코드 및 리허설 도구 해시는 유지돼야 한다. 복원 대상은 항상 별도 시험 DB이며 자동 운영 DB 복원은 없다.

시험 프로젝트·볼륨·네트워크·이미지 태그 충돌 시 중단하고 기존 자원을 정리하지 않는다. 실패·키보드 중단 시 생성한 시험 자원 정리를 시도한다. 정리 실패나 자원 잔존 시 성공으로 기록하지 않으며, 연결된 비밀 파일이 사라지지 않도록 임시 작업 공간을 보존하고 해당 경로를 출력한다. 실패·중단은 이전 성공 보고서를 failed로 무효화한다. 토큰·DSN·비밀번호·상세 Docker 오류 출력은 보고하지 않는다.

## 로컬 검증

- Python 테스트 26개 통과: 운영 변경 차단, 격리 경로·프로젝트 제한, 복원 DSN 분리, 명세·이미지 검증, 충돌 시 중단, 실패·중단 정리 및 정리 실패 시 파일 보존, 마이그레이션 결과·스키마·권한 검사, 과거 응답·헤더·최신 상태 구분, 소스 불변 필드·프로필 순서, cursor·기능 표시, 보고서 무효화와 오류 비밀 비노출.
- Docker Compose 오프라인 구성 해석 통과: 서비스 7개, 후보·이전 camera 이미지 분리, DB 이미지 고정, 시험 전용 볼륨, 내부 DB 네트워크, loopback 포트, 임시 비밀 경로와 복원 DSN 분리를 확인했다. Docker 엔진 실행 결과는 아니다.
- PGlite 임시 DB에 실제 마이그레이션과 제품의 runtime GRANT SQL을 적용했다. 새 도구의 스키마 4·5 조회 SQL과 체크섬, 열 단위 권한·역할 조회가 통과했다. 필수 소스 UPDATE 권한 누락과 불변 열 UPDATE 권한 추가를 모두 감지했다. native PostgreSQL 덤프·복원 검증을 대신하지 않는다.
- 패키지의 적용 전 검사·적용·재적용, 기존 파일·프로젝트 명세·환경·운영 기록 보존, 충돌 시 전체 쓰기 중단을 확인했다.
- 제품 Go 코드 변경이 없으므로 서버에서 통과한 08-B/08-C 전체 Go·HTTP·DB 검사를 반복하지 않았다.
