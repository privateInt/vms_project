# 작업 단위 04 — 영속 DB·장치 API 활성화

작성일: 2026-09-30 · 04-A 구현/로컬 검사 완료, 대상 서버 격리 검사 대기 · 04-B 실제 활성화는 다음 단계

## 선행 상태와 이번 단위

사용자 로그로 단위 03의 32개 파일 반영, PostgreSQL 17.11에서 장치 API·권한·동시 생성·실패 롤백·재시작/토큰 교체 보존 통과를 확인했다. 단위 03 기록에 백업 경로와 완료 상태를 추가했다.

AGENTS, 작업 기준, 최신 진행 기록을 확인했다. 이번 단위는 camera 소유 영속 DB·계정·비밀, 명시적 마이그레이션, 기존 camera 서비스 전환과 실패 복구다. 소스 CRUD·UI·미디어/모델 기능은 포함하지 않는다.

## 변경

- PostgreSQL 17.11의 영속 볼륨·비공개 내부 네트워크, 관리자/마이그레이션/runtime 역할과 초기화 파일.
- 파일 기반 DB 비밀 설정과 모호한 이중 설정 거부. 비밀의 전용 디렉터리·기존 값 유지·불완전 상태 거부.
- API/마이그레이션 Docker 이미지와 opt-in Compose 구성. 기존 .env 값은 유지하고 활성화 시 구성 선택자 한 줄만 추가.
- 백업 → 명시적 마이그레이션/권한 부여 → camera API 전환 → readiness/인증 조회 순서. 실패 시 이전 camera 이미지·설정 복구, 동시 사용자 수정 보존.
- 다른 서비스의 컨테이너 식별·시작 시각·재시작 횟수 비교. 실제 활성화 경로에 전체 프로젝트 down/볼륨 삭제 없음.
- 일반 PostgreSQL/Go 회귀 검사와 Docker 활성화·실패 복구·DB 재생성·백업 복원을 묶은 임시 검사. 코드 해시·Docker 서버가 같은 성공 기록을 실제 활성화의 선행 조건으로 사용.

| 항목 | 상태 |
|---|---|
| Go race·정적 검사 | 최종 전체 검사 통과 |
| 파일 기반 DB URL | 누락·직접/파일 충돌·파일 접근 실패·빈 값/과대/여러 줄 거부 통과 |
| 실제 API + PostgreSQL WASM | 파일 비밀로 접속, 생성·조회·멱등·API 재시작·토큰 교체 보존 통과 |
| Python 활성화 동작 검사 | 11개 통과: 비밀 재사용/권한, 기존 볼륨 보호, 잠금, 설정 충돌, 실패 복구, 사용자 수정 보존, 다른 서비스 보호 |

| 패치 적용 도구 | 7개 통과: 충돌·경로·변조 거부, 기존 파일 백업, 재적용·실패 복구 |
| 실제 Docker 활성화·DB 컨테이너 교체·복원 | 제작 환경 Docker 엔진 부재로 미실행. 서버 검사 필수 |
| 운영 활성화·실장비 | 미실행 |

WASM 통합의 첫 실행에서 API 종료가 한 차례 비정상 종료했다. 종료 진단 로그를 추가한 동일 검사의 최종 재실행은 통과했으며 원인은 확정하지 않았다. 서버 격리 검사의 첫 단계에서 일반 PostgreSQL의 Go/API 종료 검사를 다시 수행하도록 했다. WASM 통과를 Docker 인수 결과로 대체하지 않는다.

## 전달과 완료 기준

작업 시간이 길어지면 단계를 더 나누라는 사용자 요청을 반영해 04-A와 04-B를 분리했다. 이번에는 이미 구현한 패치와 격리 검사만 전달하고 실제 활성화 명령은 다음 응답에서 제공한다.

04-A 패치는 단위 03 파일 기준의 충돌 검사·백업을 수행한다. 파일 적용만으로 기존 .env나 실행 컨테이너를 바꾸지 않는다. 서버에서 test_camera_activation.py를 실행한다. 최종 status=passed, scope=camera_activation_native_docker와 복원·복구·다른 컨테이너 보존을 확인하면 04-A를 완료한다.

04-B에서는 04-A 서버 결과를 검토한 뒤 activate_camera_registry.py의 명시적 적용으로 실제 camera DB/API를 시작한다. 성공은 status=activated, scope=camera_device_registry, schema_version=2, other_services_unchanged=true다. business_runtime_ready=false는 장치 등록 범위와 영상 분석 런타임의 차이를 표시하는 정상 값이다.

당장 다음 작업은 **04-A 서버 검사 결과 확인과 04-B 활성화**다. 두 결과를 확인하면 단위 04 인수를 마무리한다. 그 이후의 기능 단위는 **소스 등록·조회**이며 실제 부모 장치·채널/프로필 관계와 멱등 저장을 구현한다.
