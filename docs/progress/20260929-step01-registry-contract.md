# 작업 단위 01 — 진행 원칙과 카메라 등록 계약

작성일: 2026-09-29 · 런타임 버전: 0.1.0-p0 유지 · 계획: v0.4 유지

## 이번 완료 범위

사용자가 요청한 "한 번에 너무 많은 작업을 하지 않고 필요한 단위로 나눠 단계별 진행"을 AGENTS와 작업 기준에 기록했다. 매 작업 시작 시 두 문서와 최신 진행 기록을 읽고, 한 단위의 완료 기준을 먼저 알리고, 검증·전달까지 마친 후 결과와 다음 단위를 보고한다. 적용 명령은 채팅에 별도 제공하는 기준을 추가하고 README의 패키지 적용 명령을 제거했다.

첫 단위로 Device·VideoSource·StreamProfile의 관계, 생성 입력, 예정 생성/조회 API, 멱등성·동시 수정·삭제 원칙을 확정했다. ADR 0003, 계약 문서, camera 소유 planned 스키마와 CCTV/XR 예제를 추가했다. 기존 SourceSpec 검증 API와 새 등록 계약은 명시적으로 구분한다.

등록 API, DB·마이그레이션, 접속 자격증명, 세션·미디어 입력은 이번에 구현하지 않았다. schema 검사 성공을 실제 등록·연결 성공으로 표현하지 않는다. Go 런타임·현재 OpenAPI·Compose·Dockerfile은 변경하지 않았다.

## 검증

- Python 기반 Draft 2020-12 스키마 검사 7개 테스트 통과: 생성 예제 4개, 필수 필드·타입·ID·이름·전송 조합·프로필 범위, 일반 입력의 비밀값/런타임 상태 거부, 기존 Profile 계약 보존.
- DB 참조·프로필 ID 중복·멱등 트랜잭션은 스키마만으로 검증하지 않는다. 등록 서비스 구현 단위의 검증 항목으로 남긴다.
- Go·프로세스·라우팅·배포 구성은 변경하지 않아 이번 단위에서 Go/race/vet·HTTP 스모크·Compose를 재실행하지 않았다. 실장비·GPU·서버 상태도 미검증이다.
- 패치 도구 테스트 7개 통과: 검사 모드 무수정, 적용·백업·재적용·기존 설정 보존, 사용자 변경·payload 변조·경로 이탈·심볼릭 링크 거부, 쓰기 실패 시 변경 파일 복구.
- 별도 전달 패치는 기준 파일 SHA-256·사용자 변경·payload 무결성을 검사하고, 기존 파일을 `var/patch-backups`에 백업한다. 적용 중 대상 파일을 동시에 편집하지 않는다. 프로세스 강제 종료·디스크 장애에 대한 전체 파일의 원자적 갱신을 보장하는 도구는 아니다.
- 대상 서버는 이 환경에서 접근하지 않았다. 서버 반영은 전달 패치 적용 결과로 별도 확인한다. 빌드·서비스 재시작은 필요하지 않다.

## 다음 단위

**카메라 플랫폼의 저장소·마이그레이션 기반**을 구현한다. 기존 계획의 PostgreSQL 후보, 실제 검증 가능한 환경, driver·마이그레이션 방식과 데이터 소유권을 확인해 ADR에 확정한다. Device·VideoSource·StreamProfile의 물리 스키마와 접속·트랜잭션 기반을 만든다.

완료 기준은 빈 DB에서 적용·재적용, 부모 참조·ID/채널/프로필 유일성·필수 필드 제약, 오류 시 상태 확인이다. 다음 단위에 HTTP CRUD 전체나 ONVIF/XR 수신을 함께 넣지 않는다. 이후 장치 등록/조회 → 소스 등록/조회 → 변경/삭제 → 연결/세션 순으로 각각 검증한다.

세부 계약: `docs/contracts/camera-registry.md`. 새 세션도 `AGENTS.md`와 `docs/development/working-standards.md` 및 이 기록을 읽고 이어간다.
