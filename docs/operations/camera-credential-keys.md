# camera 자격증명 키 최초 준비

상태: 11-B1 호스트 준비 도구 구현 · API mount·DB 자격증명 저장·운영 교체/복원 전

## 파일과 결과

도구는 `src/infra/tools/prepare_camera_credential_keys.py`다. Linux Python 3.10 이상 표준 라이브러리만 사용하며 서비스·Docker·DB·환경 파일을 호출하거나 변경하지 않는다. 실행 명령은 채팅으로 제공한다.

| 항목 | 위치·권한·의미 |
|---|---|
| 전용 디렉터리 | `var/camera/credential-keys`, 현재 실행 계정 소유·0700 |
| 키 묶음 | `key-bundle.json`, 일반 파일·하드 링크 없음·현재 계정 소유·0600 |
| 준비 잠금 | `.prepare.lock`, 현재 계정 소유·0600, 경쟁 실행 거부 |
| 암호화 키 | 독립 난수 32바이트, enc- ID·active ID·이력 |
| 멱등 비교 키 | 별도 난수 32바이트, idem- ID·active ID·이력 |

명시적 apply 없이 키를 만들지 않는다. 최초 준비 성공은 prepared, 같은 파일을 확인한 재실행은 already_prepared다. 반복 실행은 키를 교체하지 않는다. 공개 JSON에는 경로·권한·키 ID·키 개수와 상태만 반환한다. 키 원문·base64·username/password·입력 내용·OS 예외 원문을 출력하지 않는다. keys_activated_in_api는 false다.

## 보존과 실패 처리

프로젝트 루트부터 디렉터리와 파일을 descriptor 기반으로 열어 심볼릭 링크를 거부한다. 키 파일의 타입·소유자·권한·크기·읽는 동안 변경을 검사한다. 공유/배타 준비 잠금을 사용하며 이름이 바뀐 디렉터리에서 준비를 완료했다고 반환하지 않는다.

최초 파일은 전용 임시 파일을 fsync한 뒤 목적 파일이 없는 경우에만 원자적으로 게시한다. 다른 작성자가 먼저 만든 파일을 덮어쓰지 않는다. 기존 파일이 손상됐거나 권한이 틀리거나 예상 밖 파일/중단 흔적이 있으면 새 키를 자동 생성하거나 chmod로 수리하지 않고 실패한다. 복구는 기존 키/관련 데이터의 상태를 확인한 별도 작업이다.

이 도구는 최초 생성과 기존 파일 검증만 한다. 수동으로 편집한 유효 이력도 바이트를 바꾸지 않고 확인하지만, 그것이 운영 키 교체 승인을 대신하지 않는다. 키 이력은 목적별 최대 16개다. 한도 초과 시 자동 삭제하지 않는다.

키 파일은 비밀 파일이다. 일반 프로젝트 압축본·소스 저장소·출력 로그·환경 파일·패치에 넣지 않는다. root 또는 같은 계정의 키 접근을 방어하는 별도 서비스는 아직 없다. 런타임의 제한된 읽기 전용 공급과 검증은 다음 통합 작업이다.

## 백업과 복원 경계

DB pg_dump에는 이 키 파일이 포함되지 않는다. 향후 암호문 DB 백업에는 그 암호문과 멱등 지문이 요구하는 정확한 키 이력을 별도로 보호해 보관해야 한다. 키를 잃으면 재생성으로 기존 데이터를 복호화할 수 없다. 키 교체 뒤에도 관련 행/성공 journal/보존 중인 백업을 확인하기 전까지 옛 키를 폐기하지 않는다.

이번 검사는 합성 자격증명과 일회성 임시 키를 사용했다. 보호된 임시 디렉터리로 키 파일을 복사한 뒤 새 Go 프로세스가 저장한 암호문과 HMAC 지문을 같은 키 이력으로 검증했다. 운영 DB·운영 키·실제 사용자 비밀을 백업/복원한 결과는 아니다. 보호된 운영 키 백업·복구 책임·복원 후 암호화 사용량 고수위 또는 새 키 선택은 저장소/API 활성화 전에 구현·검증해야 한다.

## 이번 파일 패치와 기존 전환 기록

새 Go 파일을 명세에 포함하려고 project-manifest.json을 갱신한다. 실행 OpenAPI·기존 Go/SQL·Compose·서비스 이미지·스키마 7은 보존한다. 파일 패치와 키 준비 도구 모두 API 재시작을 하지 않는다.

10-D2 리허설 및 10-D3 전환 기록은 당시 소스 명세 hash에 묶인 과거 인수 증거다. 이번 새 명세를 그 기록으로 활성화하려 하면 이전 전환 도구의 revision 비교가 실패하는 것이 정상이다. 과거 기록의 hash를 고치거나 재사용하지 않는다. 향후 실제 API 연결은 새 코드에 맞는 preflight·격리 리허설·전환 도구와 증거를 갖춰 별도 진행한다.

자세한 암호문·멱등 지문·키 이력 결정은 [ADR 0006](../architecture/decisions/0006-camera-credential-crypto.md), 이번 인수 경계는 [11-B1 진행 기록](../progress/20261002-step11b1-credential-crypto-keys.md)을 따른다.
