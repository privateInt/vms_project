# camera 소스 API 전환·복구 기준

상태: 2026-09-30 · 05-B2 서버 검사 인수 · 05-B3 운영 전환 도구 전달 · 실제 전환 대기

## 현재 경계

운영 camera API는 `0.2.0-device-registry`, DB는 스키마 2다. 05-A의 소스 API `0.3.0-source-registry`는 스키마 3과 소스 관련 runtime 권한을 요구한다. 구버전 API는 스키마 3을 거부하므로 마이그레이션 후 구버전 이미지만 다시 시작하는 방식은 복구가 아니다.

05-B1 조회 당시 장치·장치 멱등 응답·소스·프로필은 모두 0건이었다. 이는 조회 시점의 사실이다. 실제 전환 직전에 다시 점검하며, 빈 DB라는 가정으로 데이터 삭제나 초기화를 수행하지 않는다.

## 05-B2에서 확인하는 절차

`test_camera_source_upgrade.py`는 현재 운영 상태를 읽고 별도 임시 디렉터리와 무작위 Docker 프로젝트를 만든다. 운영 이미지 태그를 덮어쓰지 않고 후보 이미지를 한 번 빌드한다. 운영 중인 구버전 camera 이미지와 PostgreSQL 이미지의 불변 ID를 사용해 시험 환경을 구성한다. 복사 대상은 05-A 배포 명세에 포함된 파일로 제한하며 운영 `.env`, 비밀, `var`, 사용자 미추적 파일은 가져오지 않는다.

1. 격리 DB에 실제 구버전 마이그레이션 실행 파일로 스키마 2를 만들고 구버전 API로 시험 장치를 등록한다.
2. 시험 API를 중지하고 DB의 다른 클라이언트가 없는지 확인한 뒤 custom-format 백업을 만든다.
3. 후보 이미지로 스키마 3 및 runtime 권한을 반영한다. 재실행 시 추가 마이그레이션이 0건인지 확인한다.
4. 새 API에서 기존 장치 조회·멱등 응답, 새 소스와 두 프로필의 생성·조회·멱등 응답, API 컨테이너 재생성 후 보존을 확인한다.
5. 백업을 별도 `vms_camera_restore` DB에 복원한다. 별도 구버전 API로 스키마 2의 readiness와 기존 장치·멱등 응답을 확인한다.
6. 원래 시험 DB의 새 소스가 그대로 남아 있는지 확인한다. 복원 검사는 스키마 3 DB를 덮어쓰지 않는다.
7. 다른 플랫폼을 대신하는 격리 sentinel 컨테이너 3개의 상태와 운영 프로젝트 컨테이너·설정·배포 명세의 불변을 확인한다.

runtime은 다섯 등록 테이블의 SELECT/INSERT와 스키마·마이그레이션 조회 권한을 사용한다. UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER 및 스키마 CREATE 권한과 역할의 superuser/DB 생성/역할 생성 권한이 없는지 확인한다.

성공 보고서 `var/camera/source-upgrade-check.json`에는 배포 명세·검사 코드의 체크섬, Docker daemon ID, 기존·후보 이미지 ID, 검증 결과를 기록한다. 검사 컨테이너·볼륨·임시 파일은 정리하고, 다음 단계에서 사용할 후보 이미지와 보고서는 유지한다. 정리에 실패하면 실패 상태와 임시 경로를 출력하며 마운트된 비밀 파일을 보존한다. 이 경우 성공 보고서를 발행하지 않는다.

운영 프로젝트에는 조회와 로컬 잠금·검사 보고서 쓰기만 수행한다. 운영 DB 마이그레이션, 업무 데이터 변경, 서비스 재시작 및 실제 소스 API 활성화는 포함하지 않는다. 전체 Go 회귀 검사는 05-A 서버에서 완료했으므로 이 도구에서 반복하지 않는다.

## 05-B3 운영 전환 및 실패 처리

`activate_camera_sources.py`를 추가했다. 명시적 적용 옵션과 기존 camera 활성화 잠금이 필요하다. 05-B2 성공 보고서의 필수 검사 결과, 검사 코드·배포 명세 체크섬, Docker daemon, 기존·후보·DB 이미지 ID를 대조한다. 미완료 전환 기록이 있으면 새 작업을 시작하지 않는다.

1. 운영 API·스키마 2·볼륨 소유권·설정·비밀 파일을 재점검하고 후보 이미지를 다시 빌드하지 않고 사용한다.
2. 기존 camera API만 중지하고 모든 다른 DB 클라이언트가 종료됐는지 확인한다. DB 컨테이너와 다른 플랫폼을 중지하거나 재생성하지 않는다.
3. `var/camera/source-activation-backups/step05b3-*`에 기존 설정·컨테이너 상태와 DB 백업을 보존한다. 백업 형식·목록과 중지 전후 스키마·건수를 확인한다.
4. `.env`의 기존 값을 보존하고 `VMS_CAMERA_IMAGE`에 검증된 이미지 ID를 추가한다. 스키마 3과 runtime 권한을 반영하고 기존 테이블 건수 보존을 확인한다.
5. camera API만 검증된 이미지로 시작한다. readiness·버전·소스 capability·인증된 GET 조회를 확인한다. 운영 DB에 시험 레코드를 생성하지 않는다.

진행 단계와 결과는 백업 폴더의 `result.json` 및 `var/camera/source-activation.json`에 기록한다. 성공 후 같은 도구를 다시 실행하면 현재 상태를 조회해 `already_activated`를 반환하며 재시작·재마이그레이션하지 않는다. 이미지 ID는 `.env`에 고정되므로 전환 도구의 실행 환경이 종료돼도 유지된다.

마이그레이션을 요청하기 전에 실패한 경우에만 스키마 2와 원래 컨테이너·설정·비밀 파일의 상태를 확인하고 기존 API를 다시 시작한다. 동시 설정 변경은 덮어쓰지 않는다. 마이그레이션 요청 이후에는 명령 실패만으로 DDL 미반영을 단정할 수 없으므로 후보 설정과 현재 DB를 유지하고 별도 복구 판단을 요구한다. 실패 기록을 삭제해서 강제로 다시 실행하지 않는다.

마이그레이션 이후 실패했다고 DB를 자동으로 백업 시점으로 되돌리지 않는다. 새 API가 요청을 받은 이후에는 백업에 없는 장치·소스·멱등 응답이 생길 수 있다. 이 경우 현재 DB와 후보 이미지·진행 기록을 보존하고 현재 스키마에 맞는 API의 재시작 또는 수정으로 복구한다. 구버전 이미지만 재시작하지 않는다.

백업 복원은 우선 별도 DB에서 원본 데이터 보존과 구버전 API 호환성을 확인하는 수단이다. 이를 운영 대상으로 바꾸는 일은 쓰기 중단 시점과 이후 데이터 유무를 확인한 별도 복구 절차다. 05-B2 서버 성공은 격리 환경의 업그레이드·별도 복원 가능성을 뜻한다. 05-B3 전환 도구의 분기·실패 처리는 로컬 모의 검사로 확인했으며 실제 서버 전환 완료는 해당 실행 결과로 별도 인수한다.
