# 프로젝트 구조와 작업 기준

상태: 채택 · 2026-09-29 · 사용자 요구사항을 작업 기준으로 반영

## 판단

`src` 아래 구현을 모으고 그 안에서 `platform`과 `infra`를 나누는 제안은 타당하다. 제품의 책임과 실행 기반을 구분하고, 루트의 `docs`를 통해 설계·작업 이력을 코드와 함께 관리할 수 있다. 다만 폴더를 나누는 것만으로 독립 플랫폼이 되지는 않는다. 데이터 소유권, API 계약, 실행·배포 경계도 함께 지킨다.

## 확정한 배치

| 경로 | 포함하는 것 | 경계 |
|---|---|---|
| `src/platform/camera` | API·ONVIF/PTZ·RTSP/XR 어댑터·소스와 세션·녹화 모듈 | 모델 선택·추론 작업 스케줄링은 소유하지 않음 |
| `src/platform/model` | 모델 버전·아티팩트 참조·배포·런타임·학습 관리 | 카메라 연결이나 분석 규칙은 소유하지 않음 |
| `src/platform/analysis` | 분석 작업·세션별 실행·워커 임대·추론 연결·추적·이벤트 | 모델 배포와 카메라 접속 수명은 API로 요청 |
| `src/platform/operation` | 관제·업무 조율·알림·사용자 작업 | 다른 플랫폼 DB 직접 수정, 워커 직접 재시작 금지 |
| `src/platform/internal` | 현재 Go 서비스의 HTTP·인증·종료 같은 공통 기술 코드 | 도메인 엔티티·공유 DB·업무 상태 금지 |
| `src/infra` | 공용 DB·브로커·객체 저장소 배포 설정, 설치·검증·운영 도구 | 특정 플랫폼의 업무 로직은 해당 플랫폼으로 이동 |
| `docs` | 요구사항·설계·ADR·운영·작업 기록 | 실행 코드 원본은 `src`에 배치 |

각 플랫폼은 `cmd`, `internal`, `api`를 시작 구조로 사용한다. 필요한 경우 `web`, `worker`, `migrations`, `adapters` 등을 해당 플랫폼 내부에 추가한다. Go 이외 언어도 소유 플랫폼 아래에 둔다. 플랫폼 전용 Dockerfile·Compose·설정은 플랫폼과 함께 변경할 수 있도록 해당 폴더에 둔다. 공용 인프라 설정은 `src/infra`에 둔다. 루트 `compose.yaml`은 이를 조합하는 진입점이다.

테스트는 기능 코드 옆, API 명세·JSON Schema·예제는 소유 플랫폼 `api` 아래, 설명 문서는 `docs` 아래 둔다. 루트에는 README·AGENTS·Makefile·Compose·환경 예제·패키지 메타데이터만 배치한다. 생성 바이너리는 `build`, 로컬 데이터는 `var`에 두고 버전 관리에서 제외한다.

## 독립성의 의미

- 단일 저장소와 초기 단일 Go 모듈은 허용한다. 각 API는 별도 프로세스·이미지·Compose로 실행할 수 있어야 한다.
- `camera/internal` 등 Go `internal` 경계를 이용해 다른 플랫폼이 업무 코드를 직접 가져오지 못하게 한다.
- 저장소가 추가되면 플랫폼별 DB 또는 스키마·DB 계정·마이그레이션 소유권을 분리한다. 단위 02에서 camera 전용 저장소 모듈을 추가했다. 단위 03에서 장치 API의 선택적 저장소 연결을 구현했다. 운영 DB 배포·실행 서비스 전환은 단위 04로 분리했다. 전용 DB·역할·비밀·백업·격리 검사를 준비하고 같은 코드의 서버 검사 성공 후 camera 서비스만 전환한다. 실제 인수 여부는 최신 진행 기록을 따른다.
- 계약은 소유 플랫폼이 버전을 관리한다. 호출자는 계약을 통해 접근하고 공유 테이블이나 암묵적인 전역 객체를 만들지 않는다.
- 독립 릴리스나 서로 다른 의존성 주기가 필요해지면 플랫폼별 Go 모듈로 분리한다. 현재는 공통 기술 코드와 도구 운영을 단순하게 시작한다.

## 변경과 완료 기준

책임 경계·언어·영속 모델·배포 구조 변경은 `docs/architecture/decisions`에 이유, 대안, 채택 결과와 검증 상태를 남긴다. Go를 전 영역에 강제하지 않으며 기존 코드·앱을 반드시 재사용하지 않는다. 구현 계획은 기간보다 단계의 선행 조건과 완료 기준을 따른다.

검증 결과는 환경과 범위를 함께 쓴다. HTTP health 성공은 ONVIF 연결·XR 미디어 수신·GPU 추론 성공이 아니다. 실제 장비를 사용하지 않은 검증은 그 사실을 기록한다. 소스 작성, 로컬 실행, 대상 서버 설치, 실장비 인수는 각각 구분한다.

## 작은 작업 단위로 진행 — 2026-09-29 사용자 요청

한 번에 너무 많은 기능을 구현하지 않는다. 매 작업 시작 시 `AGENTS.md`, 이 문서, `docs/progress`의 최신 기록을 읽어 완료된 단계와 남은 항목을 확인한다. 사용자가 새 세션을 시작하거나 계속 진행하라고 요청해도 이 기준을 먼저 적용한다.

1. 이번에 끝낼 결과를 한 문장으로 정하고 범위·완료 기준·필요한 검증을 먼저 알린다.
2. 독립적으로 적용하고 결과를 확인할 수 있는 단위 하나를 선택한다. 예를 들어 등록 계약, 저장소·마이그레이션, 장치 CRUD, 소스 CRUD, 연결 세션, CCTV 입력을 각각 나눈다.
3. 선택한 단위를 실제로 완결하는 데 필요한 변경·테스트·문서·패키지 작업은 함께 수행한다. 한 기능을 확인할 수 없을 정도로 잘게 나누거나, 계획을 설명하는 데서만 멈추지 않는다.
4. 진행 중 새로운 업무 기능이나 별도 완료 기준이 필요한 일이 나오면 다음 단위로 기록한다. 현재 결과를 완성하는 데 꼭 필요한 수정은 현재 단위에서 해결한다.
5. 현재 단위에 필요한 검증을 마치면 선택적 전면 재검사나 다음 플랫폼 구현으로 범위를 넓히지 않는다. 수행한 검증과 하지 못한 검증을 구분한다.
6. 단위 종료 시 `docs/progress`에 변경·검증·남은 작업·다음 단위의 완료 기준을 남기고 사용자에게 결과를 전달한다. 이번에 승인된 작업의 필수 절차마다 확인 질문을 반복하지 않는다.
7. 패치 적용 명령은 채팅에서 따로 제공한다. README·설계·진행 기록에는 명령을 복사하지 않고 변경 내용과 적용 전제만 기록한다.

### 작업 시간이 길어질 때 — 2026-09-30 사용자 재확인

같은 기능 영역이라도 준비·격리 검사·실제 서비스 전환처럼 결과를 따로 확인할 수 있으면 하위 단계로 나눈다. 이미 준비한 결과는 해당 단계의 필수 검증을 마쳐 먼저 전달하고, 후속 실행까지 한 응답에 묶어 작업을 길게 늘리지 않는다. 단위 04는 **04-A: 패치 준비·전달과 서버 격리 검사**, **04-B: 검사 결과 확인 후 실제 camera 활성화**로 나눈다. 단위 04는 두 단계와 완료 기록 반영까지 인수를 마쳤다. 단위 05도 **05-A: 소스 등록·단건 조회 코드와 격리 검사**, **05-B: 실제 서버 반영**으로 나눈다. 각 서버 결과를 확인한 뒤 다음 단계의 범위와 실행 절차를 제시한다.

P0-A 이후에는 등록 계약 → 저장소·마이그레이션 → 장치 등록·조회 구현 → 장치 API 운영 활성화 → 소스 등록·조회 순으로 단위를 나눈다. 각 단위의 실제 완료 상태는 최신 진행 기록을 기준으로 판단한다. 세부 순서는 [카메라 등록 계약](../contracts/camera-registry.md)을 참고하고 검증 결과에 맞춰 조정하되 하나의 결과를 끝낸 뒤 보고한다.

## Codex 자동 개발과 최신 작업 순서 — 2026-10-12

사용자는 이 프로젝트를 Codex에 이관해 자동 개발을 진행하기로 했다. 현재 대화에서는 기능 개발을 중단하고 이관 자료만 준비한다. 후속 Codex의 첫 선택 단위는 [이관 문서](codex-handoff.md)의 H01이며, [backlog](codex-backlog.md)의 선행 조건·완료 기준으로 이후 개발을 진행한다. 과거 진행 기록의 다음 단계는 당시의 이력이며 현재 우선순위가 아니다.

자동 개발 요청이 있는 세션에서는 위의 작은 단위 원칙을 각 단위의 범위·검증·기록 기준으로 적용한다. 단위가 끝날 때마다 임의로 전체 개발을 중단하거나 재승인을 요구하지 않고 승인된 독립 단위를 계속 수행할 수 있다. 필요한 외부 입력/실제 증거/운영 실행 범위가 없으면 의존하는 실행은 멈추고 blocked 사유를 보고한다. 실제 검증 없는 완료 표시나 다음 기능을 한 번에 큰 변경으로 묶는 것은 허용하지 않는다.

사용자의 백업 제외·정리 결정이 최신 기준이다. 백업 추가 검토/복원 개발·자동 백업 생성을 선행 조건으로 넣지 않는다. 과거 도구의 backup 옵션은 자동으로 다시 실행하지 않는다. 현재 설정·키·자료·receipt 및 소유권/권한/인수 검사는 보존한다. 운영 실행은 이관의 코드/격리 개발 범위와 별도로 다루고, 이미 제공된 사용자 권한이 있으면 중복 확인하지 않는다.
