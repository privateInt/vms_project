# 카메라 등록 계약 — 첫 작업 단위

상태: 단위 04 장치 API 서버 인수 완료 / 단위 05-A 소스 생성·단건 조회 코드 구현, 서버 인수 대기

단위 01에서 장치와 영상 소스의 생성 입력·관계·등록 동작을 확정했다. 당시 기계 판독 계약과 예제는 `src/platform/camera/api/planned`에 보관한다. 단위 03부터 실제 장치 생성·응답 명세는 `src/platform/camera/api/openapi.json`을 따른다. 단위 05부터 SourceCreate와 소스 응답도 실행 OpenAPI를 따른다. 기존 `/api/v1/sources/validate`와 그 SourceSpec은 변경하지 않는다.

## 데이터 소유권과 관계

| 자원 | 의미와 관계 | 식별·변경 규칙 |
|---|---|---|
| Device | 물리적 CCTV·스마트글래스·시험 장치. camera 소유 | 안정된 `device_id`. IP·접속 번호로 자동 생성하지 않음. `device_kind`는 생성 후 불변 |
| VideoSource | 장치가 제공하는 논리 영상 채널. Device 하나에 여러 소스 허용 | 안정된 `source_id`, 부모 `device_id`, 장치 내 `channel_key`. 세 값은 생성 후 불변 |
| StreamProfile | 소스가 제공할 스트림의 선언 프로필 | `(source_id, profile_id)` 유일. 선언된 코덱·크기·FPS는 실제 협상 결과와 구분 |
| ConnectionConfig | 이후 구현할 어댑터별 접속 설정·자격증명 참조 | 일반 Device/Source 생성 입력과 분리. 원본 비밀번호를 응답·로그에 반환하지 않음 |
| SourceSession | 이후 실제 입력 어댑터의 접속을 구분할 런타임 자원 | 등록만으로 세션을 만들지 않음. 입력 재접속 시 새 ID·epoch. 생성 API는 이번 범위 밖 |

서버는 Device ID와 Source ID의 유일성을 각각 보장한다. `(device_id, channel_key)`도 유일하게 관리한다. IP/포트만으로 영상 채널의 유일성을 제한하지 않는다. 삭제 이력에 있는 ID와 장치/채널 키를 재사용하는 정책은 기본적으로 허용하지 않는다. 같은 논리 채널을 복원하는 기능이 필요하면 별도 복원 절차로 다룬다.

`device_kind`와 ONVIF/PTZ의 실제 지원 상태는 장치의 책임이다. 새 소스 생성 요청에는 이를 중복 저장하지 않는다. 지원 여부가 조회되지 않은 상태를 false로 확정하지 않고 `UNKNOWN`으로 표현할 수 있어야 한다. 등록자는 실제 PTZ 지원을 확정할 수 없으며 후속 ONVIF 어댑터가 관측 결과를 기록한다.

## 생성 입력

두 생성 요청은 `schema_version: v1`을 사용한다. 단위 05에서 source_id의 정확한 문자열 `validate`를 기존 검증 경로 보존을 위한 예약 값으로 확정했다. 다른 ID·채널 규칙은 유지한다. ID는 기존 P0-A와 같은 ASCII 1~64자 규칙을 따른다. 이름은 공백만으로 구성할 수 없으며 최대 128자다. 입력 ID는 호출자가 지정한다. 같은 이름을 사용한다고 같은 장치로 자동 합치지 않는다.

| 요청 | 필수 필드 |
|---|---|
| DeviceCreate | `schema_version`, `device_id`, `display_name`, `device_kind` |
| SourceCreate | `schema_version`, `source_id`, `device_id`, `channel_key`, `display_name`, `transport`, `input_mode`, `motion_mode`, `profiles` |

장치 종류는 CCTV/SMART_GLASSES/TEST, 전송 조합은 RTSP/PULL 또는 WEBRTC/PUSH다. 특정 장치 종류를 특정 전송 방식에 강제 연결하지 않는다. XR은 ONVIF/PTZ 선언 없이 등록할 수 있다. 프로필은 1~8개이며 필드·범위는 현재 SourceSpec의 Profile과 일치시킨다. 동일 소스의 프로필 ID 중복은 등록 서비스에서 거부해야 한다.

URL·사용자명·비밀번호·토큰·`credential_ref`는 이 두 요청에 넣지 않는다. 이후 연결 설정 전용 계약에서 다룬다. 따라서 지금 정의한 등록은 인벤토리와 프로필 저장이고, 연결 가능 검증을 포함하지 않는다.

현재 P0-A SourceSpec과 새 SourceCreate는 별도 계약이다. 이전 validate 요청에 포함되는 `device_kind`, `capabilities`를 새 등록 요청에 그대로 넘기지 않는다. 기존 검증 API는 유지하고 실제 생성 API를 구현할 때 새 계약으로 명시적으로 구분한다.

## 후속 API의 동작 기준

아래 Device 세 경로는 단위 03에서 구현하고 04에서 서버에 활성화했다. 단위 05-A는 Source 생성·단건 조회를 구현했으며 소스 목록은 예정이다. 신규 코드의 실제 서비스 반영은 05-B로 분리한다.

| API (Source 목록만 예정) | 동작과 응답 기준 |
|---|---|
| POST `/api/v1/devices` | DeviceCreate 저장. 성공 201. 응답에 생성 자원·version=1·생성/수정 시각 포함 |
| GET `/api/v1/devices/{device_id}` | 저장된 장치 조회. 성공 200, 없음 404 |
| GET `/api/v1/devices` | 장치 목록. `limit` 기본 50·최대 200, 불투명 cursor와 다음 cursor 제공 |
| POST `/api/v1/sources` | SourceCreate 저장. 실제 Device 존재와 프로필 ID 중복 검사. 성공 201 |
| GET `/api/v1/sources/{source_id}` | 저장된 소스 조회. 등록과 영상 수신 상태를 분리해 반환 |
| GET `/api/v1/sources` | 소스 목록. `limit` 기본 50·최대 200, ID 오름차순·cursor, 선택적 `device_id` 일치 필터. 코드 단위 06-A 구현, 운영 반영 대기 |

생성 시각·수정 시각은 서버 UTC로 기록한다. 응답에는 요청 ID를 포함한다. 장치·소스 조회는 인증이 필요하다. 페이지 순서는 ID 오름차순으로 고정하고 cursor를 필터와 결합해 검사한다. 페이지 사이의 동시 변경에 대해 스냅샷 일관성을 보장한다고 가정하지 않는다. 소스 cursor는 필터 없는 상태까지 구분하며 다른 장치 필터나 장치 목록 cursor를 사용하면 400 QUERY_INVALID다. limit은 페이지 사이에 변경할 수 있다. 없는 device_id 필터는 200과 빈 items/next_cursor=null을 반환한다. 한 페이지의 소스와 프로필은 같은 SQL 스냅샷으로 읽는다.

생성 요청에는 `Idempotency-Key`를 요구한다. 유효 길이는 1~128 ASCII 표시 문자로 제한한다. 같은 인증 주체·메서드·경로·키와 같은 정규화 요청이면 같은 자원과 응답을 반환하고, 다른 요청이면 409를 반환한다. 자원 저장과 성공 응답 기록은 한 트랜잭션으로 확정한다. HTTP 요청 ID는 매 요청마다 달라질 수 있으며 멱등 키와 구분한다. 초기에는 고정 개발 토큰 인증 주체를 사용하고 향후 IAM 전환 시 주체 범위를 유지한다.

멱등 비교의 정규화는 JSON 객체 키 순서를 무시하고 필드 값과 배열 순서를 보존하는 방식이다. 문자열을 임의로 trim하거나 타입을 변환하지 않는다. 초기 멱등 기록은 자동 만료시키지 않는다. 만료 정책을 추가할 때는 재시도 보장 기간과 ID 재사용 금지를 함께 명시한다.

서로 다른 키로 같은 ID나 장치/채널을 생성하면 409다. 부모 Device가 없거나 삭제 상태라면 소스 생성은 409 `DEVICE_UNAVAILABLE`다. 잘못된 JSON·필드 타입은 400, 인증 실패 401, 본문 제한 413, Content-Type 오류 415, 필드 의미·프로필 중복 오류 422, 저장소 이용 불가는 503으로 구분한다. 현재 HTTP 기반의 64 KiB 요청 제한을 유지한다.

생성·조회 외 수정/삭제 API의 세부 요청·응답은 해당 구현 단위에서 별도 확정한다. 수정은 version 조건으로 동시 변경을 감지하고, 장치 삭제는 자식 소스가 있으면 거부한다. 소스 삭제는 사용 중인 소비 관계와 세션 정리를 확인해야 하며, 실제 정리 전에 완료로 표시하지 않는다. 녹화 데이터는 장치 삭제와 함께 자동 삭제하지 않는다.

## 이후 구현 위치와 완료 기준

단위 01에서 위 논리 관계를 채택했다. 단위 02에서 PostgreSQL·pgx·SQL 마이그레이션을 구현했다. 소스의 primary_profile_id는 첫 프로필을 참조하는 내부 저장 필드이며 생성 요청에는 추가하지 않는다. 저장소 로컬 검증과 대상 서버 검증의 구분은 최신 진행 기록과 ADR 0004를 따른다.

| 단위 | 범위 | 완료 기준 |
|---|---|---|
| 01: 등록 계약 | Device/Source 생성 스키마·예제·소유권·오류 규칙 | 정상/오류 예제 검사, P0-A 런타임 유지, 미구현 범위 기록 |
| 02: 저장소 기반 | camera 데이터 스키마·마이그레이션·접속·트랜잭션 기반 | 빈 DB 적용·재적용, 필수 관계/유일성 제약, 마이그레이션 오류 확인 |
| 03: 장치 등록·조회 구현 | Device 생성·조회·목록과 멱등 처리 | 실제 API/DB 통합 검증, 재시작 후 동일 데이터, 중복 요청 방지 |
| 04: 장치 API 운영 활성화 완료 | 영속 DB·역할·비밀·마이그레이션·camera 서비스 전환 | 격리 검사 선행, readiness·저장·DB 재시작 보존 |
| 05-A/B: 소스 등록·단건 조회 | 부모 참조·채널·프로필 저장, 구현/격리 검사와 실제 반영 분리 | 다중 채널, 부모 참조 오류·프로필 중복 거부, 재시작 보존 |
| 이후: 변경·삭제 | version·사용 관계·정리 상태 | 동시 수정·부분 실패·종속 자원 보호 |
| 이후: 연결·세션 | 접속 설정·자격증명·세션·어댑터 | 등록과 실제 수신 구분, 단절·재접속·이전 세션 격리 |

프레임·추론·이벤트·UI는 이 단위에 포함하지 않는다. 각 단위를 마친 뒤 결과와 다음 단위를 보고한다.
